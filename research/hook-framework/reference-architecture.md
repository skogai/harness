# Reference architecture: claude-code-hooks

Architectural patterns extracted from `/home/skogix/.local/src/claude-code-hooks`
(a mature, single-purpose sound-notification hook framework for Claude Code) for
reuse when fixing the four earlier hook-framework attempts in this repo
(`.claude/hooks/`, `marketplace/plugins/skogharness/`, `marketplace/plugins/skoghooks/`,
`marketplace/plugins/skogix-hooks/`). See [attempts-review.md](./attempts-review.md)
for the per-attempt gap analysis and [plan.md](./plan.md) for the fix plan.

## Architectural patterns worth copying

1. **One dispatcher script, not one script per hook.** `hooks.py` (483 lines) is invoked identically for all 30 hook events; it reads `hook_event_name` from the stdin JSON and looks up behavior in a dict (`HOOK_SOUND_MAP`). No per-event script duplication.
2. **Two-tier config with local override, same shape for two different concerns.** `hooks-config.json` (shared, committed) + `hooks-config.local.json` (gitignored, personal) — local wins if the key is present, else falls back to shared, else defaults to enabled. The exact same local-override pattern is used again for `settings.local.json`'s `disableAllHooks`. One fallback function (`is_hook_disabled`), reused, not reimplemented per hook.
3. **Fail-open, never block the agent.** Every error path (bad JSON, missing config file, missing sound file, missing audio player, unexpected exception) falls through to `sys.exit(0)`. `main()` wraps everything in try/except with `json.JSONDecodeError` caught separately. A notification hook framework should never be able to break the host session.
4. **Path traversal guard on user/config-influenced input.** Before building a filesystem path from `sound_name`, it rejects any value containing `/`, `\`, or `..`. Cheap, easy to forget, present here.
5. **Cross-platform playback abstraction with graceful degradation.** `get_audio_player()` tries a preference-ordered list of Linux players (`paplay` → `aplay` → `ffplay` → `mpg123`) via `which`, uses `afplay` on macOS, `winsound`/PowerShell on Windows, and returns `None` (silently skip) if nothing is found. Windows note worth remembering: uses `SND_SYNC` not `SND_ASYNC` because the script process exits immediately after the call, which would kill async playback before it finished — a real gotcha, documented inline.
6. **Extensible pattern-matching table instead of hardcoded conditionals.** `BASH_PATTERNS = [(regex, sound_name), ...]` maps command substrings (e.g. `git commit`) to special sounds. Adding a new special-cased command is a one-line table entry, not a new `if`.
7. **Separate map for agent-context hooks, discovered empirically.** Official docs undercount which hooks fire inside subagents/skills. This repo tested it and found 6 (`PreToolUse`, `PostToolUse`, `PermissionRequest`, `PostToolUseFailure`, `Stop`, `SubagentStop`), kept them in their own `AGENT_HOOK_SOUND_MAP` with `agent_*` sound folders, invoked via a `--agent=<name>` CLI flag threaded through the agent's frontmatter hook command. Don't trust hook docs blindly — verify empirically and note discrepancies.
8. **Logging and muting are independent axes.** `is_logging_disabled()` and `is_hook_disabled(event)` are separate checks — you can silence sound but keep the audit log, or vice versa. Log entries strip `transcript_path`/`cwd` (noisy, not useful) and tag `invoked_by_agent` only when relevant.
9. **Documentation treated as a regression surface, not a one-time write-up.** `HOOKS-README.md` (602 lines) tracks: the official hook table, a "Not in Official Docs" table for hooks/fields found only in the changelog or schema introspection, known bugs with upstream GitHub issue links and live status, a full matcher reference per hook, and per-hook decision-control schemas. This is unusually thorough versus a typical hook repo's README.
10. **Automated drift-detection workflow.** `/workflows:workflow-changelog` launches two independent research agents in parallel (one repo-aware, one general web research), cross-references their findings, runs them against an append-only `verification-checklist.md` (a growing regression suite for "things that broke before"), and appends dated, status-tracked entries (`NEW`/`RECURRING`/`RESOLVED`) to a changelog file rather than ever overwriting history.
11. **Automated hook-addition workflow with mandatory re-verification.** `/workflows:workflow-add-hook` is a checklist that touches ~14 files (settings ×4, config, script, two READMEs, presentation, test agent, three demo files) with exact per-platform differences called out (`python` vs `python3`, `${CLAUDE_PROJECT_DIR}` vs relative path) and ends by re-`grep`-ing every file for the new hook name — it does not trust that an edit tool call succeeding means the edit is correct/complete.
12. **Consistency-as-correctness discipline.** CLAUDE.md explicitly states the hook count must match across ~14 locations and treats a mismatch as a bug. The workflow performs a "stale count sweep" (targeted greps for old counts in prose, not just structured fields) after every edit — most repos would leave prose descriptions stale.
13. **Vendoring-style install, zero build step.** Install is: clone repo to temp dir → copy `.claude/hooks/*` into the target project → manually splice `disableAllHooks` + `hooks` keys from `install/settings-<platform>.json` into the project's own `.claude/settings.json` (merge, not overwrite) → start `claude` and listen for the startup sound. No package manager, no plugin registry, no install script. Only prerequisites: Python 3 and a platform audio player (usually already present). Tradeoff to note: no auto-update path — picking up upstream changes means repeating the clone+copy manually.
14. **Per-OS settings files instead of one file with runtime OS detection.** `install/settings-{mac,linux,windows}.json` differ only in the command string; this sidesteps needing shell conditionals inside the hook command itself.
15. **`statusMessage` set to the hook's own name on every hook entry** — near-free UX: the spinner shows which hook is currently firing.
16. **`once: true` used narrowly and deliberately** (only `PreCompact`, `SessionStart`, `SessionEnd`) rather than applied broadly — it's a documented convention with a stated reason (session-lifecycle events that should fire once), not a default.

## Installation process (representative of all 3 platforms, from `install/README-linux.md`)

1. Prereqs: Python 3 (`python3 --version`), platform audio player (`paplay` from `pulseaudio-utils` on Linux; built-in `afplay` on macOS; built-in `winsound` on Windows).
2. `mkdir -p .claude/hooks`, clone the repo to a temp dir, `cp -r temp-hooks/.claude/hooks/* .claude/hooks/`, delete the temp clone.
3. Create `.claude/settings.json` if absent; copy the `disableAllHooks` and `hooks` keys out of `install/settings-<platform>.json` into it (merge into existing settings, don't replace the file).
4. Start `claude` — hearing the session-start sound confirms success. Missing-prereqs failure mode is a `SessionStart:startup hook error`.
5. Optional: copy `.claude/agents/claude-code-hook-agent.md` in and run `/agents claude-code-hook-agent` to demo the 3 agent-scoped hooks (weather-fetch demo).
